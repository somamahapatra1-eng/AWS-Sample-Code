Multi-stage CI/CD pipeline

A multi-stage CI/CD pipeline starts with a trigger, then moves code through fixed steps. Each step must succeed before the next one starts.

Trigger

An event starts the pipeline. Nothing runs until a trigger fires.

  • Code push. A commit or merge to a branch starts the pipeline. This is the most common trigger.
  • Pull request. Opening or updating a merge request starts build and test only. Deploy waits until the change is merged.
  • Tag or release. Creating a version tag starts a release pipeline, often for production.
  • Schedule. A timer starts the pipeline at a fixed time, such as every night.
  • Manual. A person starts the pipeline from the tool. This is used for a controlled release.
  • Webhook. Another system sends an event, and that event starts the pipeline.

Source

After the trigger, the pipeline takes the code from the repository and saves it as an input.

Build

The pipeline compiles or packages that code. It produces a build artifact that later stages can use.

Test

Automated checks run on the build. The pipeline stops here if tests fail.

Deploy

The tested artifact is released to the target environment, such as development, staging, or production.

Order

The trigger runs the pipeline once. After that, Source, Build, Test, and Deploy run one after another.

Stop on failure

If any stage fails, later stages do not run.

Artifacts

Each stage passes its output to the next stage through shared storage.

CI vs CD

Build and test are continuous integration. Deploy is continuous delivery.
