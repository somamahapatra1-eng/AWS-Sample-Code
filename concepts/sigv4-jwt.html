SigV4 vs JWT: Two Ways to Prove Identity

The Problem

An API needs to know who is calling it. Both SigV4 (AWS signature) and JWT (JSON Web Token) prove identity, but they work very differently.

SigV4: AWS Native Signing

SigV4 is AWS's request-signing protocol. The caller holds an AWS access key (like a username/password pair). Before sending the request, the caller computes a cryptographic signature of the request and includes it in the HTTP header. The API verifies that signature using AWS Identity and Access Management (IAM) and knows who made the request by looking up the access key. 

Authorization: AWS4-HMAC-SHA256 Credential=AKIAIOSFODNN7EXAMPLE/20131124/us-east-1/s3/aws4_request, SignedHeaders=host;range;x-amz-content-sha256, Signature=...

Who it works for:

  • AWS services calling each other (Lambda → S3)
  • IAM users or roles (a service inside AWS, or a human with an access key)
  • IAM Roles Anywhere (a machine outside AWS with a certificate; it assumes an IAM role and signs requests)
In a Lambda: The Lambda has an execution role. That role has AWS credentials automatically. When the Lambda calls SQS or S3, boto3 signs the request with SigV4 using the role's credentials. The service verifies it and allows the call.

JWT: Stateless Identity Token

JWT is a token-based protocol. A user logs in to an identity provider (like Cognito or Okta) with a username and password. The provider issues a JWT — a signed JSON object that says "I certify that this person is user@example.com and their email is verified." The token is valid for a time (e.g., 1 hour). The user then sends the JWT to the API in an HTTP header. 

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Who it works for:

  • End users (a person logging into a web or mobile app)
  • Third-party services that have a user account with you
  • Any client that can store a token in memory or a cookie
In API Gateway: Configure a Cognito authorizer. API Gateway validates the JWT signature and extracts claims like cognito:username. The Lambda receives the claims in event.requestContext.authorizer.claims.

Side-by-Side Comparison

Feature SigV4 JWT
Credential type AWS access key (ID + secret) Token (looks like a random string)
Who issues it AWS IAM (built-in) Identity provider (Cognito, Okta, Auth0)
Verification API calls AWS IAM to verify API checks the token signature locally
Caller identity Assumed-role ARN (e.g., arn:aws:sts::123456789012:assumed-role/my-role/session-name) Claims in the JWT (e.g., sub, email, groups)
Best for Service-to-service, machines, things with AWS credentials End users, external clients, time-limited access
Revocation Immediate (delete/rotate the access key) Delayed (token valid until it expires)

In Practice: One Lambda, Two Callers

The same Lambda can accept both. API Gateway runs two authorizers in parallel and the Lambda receives whichever one succeeded. 

def identify_caller(event):
    request_context = event.get("requestContext", {})
    authorizer = request_context.get("authorizer", {})
    
    # JWT path: Cognito authorizer populated claims
    username = authorizer.get("claims", {}).get("cognito:username")
    if username:
        return {"method": "jwt", "caller": username}
    
    # SigV4 path: IAM authorizer populated the assumed-role ARN
    user_arn = request_context.get("identity", {}).get("userArn")
    if user_arn:
        return {"method": "sigv4", "caller": user_arn}
    
    raise PermissionError("No valid credentials")

When to Choose Which

Use SigV4 if:

  • The caller is a Lambda, ECS task, or another AWS service
  • The caller is outside AWS but has AWS credentials (IAM Roles Anywhere)
  • You want immediate revocation
  • The caller cannot manage JWTs

Use JWT if:

  • The caller is a human or external service
  • You want to delegate authentication to a separate provider
  • The token needs custom claims (e.g., department, role)
  • You want stateless verification (API doesn't call IAM on every request)
