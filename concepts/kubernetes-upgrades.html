Kubernetes Cluster Upgrades: AKS & EKS

The Challenge

Kubernetes clusters need regular updates for security patches and new features. On AKS or EKS, you cannot skip minor versions (e.g., 1.33 → 1.35 is a two-hop: 1.33 → 1.34 → 1.35). The control plane and nodes must stay within one minor version of each other.

Upgrades touch every workload. Workload health checks, PodDisruptionBudgets, and resource constraints can block the upgrade. The strategy is: validate early, drain one node at a time, wait for workloads to reschedule, and roll back on failure.

AKS Upgrade (1.33 → 1.34 → 1.35)

Prerequisites

  • Admin SSH access to a bastion or admin node
  • kubeconfig valid and pointing to the target cluster
  • All nodes currently healthy and reachable
  • No unhealthy pods or resource constraints blocking drains

Two-Hop Upgrade Path

Azure requires upgrading one minor version at a time. If you want to go from 1.33 to 1.35: 

1.33 (current) → 1.34 (intermediate) → 1.35 (target)

Each hop follows the same steps:

  1. Update control plane — Azure drains the control plane nodes and applies the update.
  2. Drain each node pool — For each node pool, cordon nodes and evict workloads gracefully.
  3. Update node images — Replace the VM image with the new Kubernetes version.
  4. Drain wait loop — Monitor node readiness. Pods reschedule to remaining nodes.
  5. Verify health — All nodes report ready. All pods running or completed.

Upgrade Automation Script

The aegis repo uses a Python upgrade script (`upgrade.py`) that:

  • Tracks phase state in a config file so it can resume on failure
  • Detects partial upgrades and skips completed phases
  • Handles memory pressure on crowded node pools (evicts low-priority pods)
  • Validates PodDisruptionBudgets before draining
  • Automatically remediates known failure modes (e.g., evicted pods left behind)

Config Structure (config.yaml)

version: 1
cluster_name: aks-prod
control_plane_upgrade:
  status: completed | in_progress | pending
  version: 1.34
node_pool_upgrades:
  - name: system
    status: pending
    version: 1.34
    drain_complete: false
  - name: workload
    status: pending
    version: 1.34
    drain_complete: false

EKS Upgrade (1.33 → 1.35)

Key Differences from AKS

EKS upgrades are more hands-off but have different constraints:

Aspect AKS EKS
Control plane update Azure manages; you trigger via CLI/portal AWS manages; you trigger via CLI/console
Node update Manual (cordon, drain, update AMI) Auto via Launch Template (rolling replace)
Skip support No — must upgrade 1.33 → 1.34 → 1.35 No — same two-hop rule
Workload downtime Controlled by drain policy Depends on PDB and replica count

EKS Upgrade Steps

  1. Check compatibility — CNI, add-ons, and workloads compatible with new version
  2. Update control plane — aws eks update-cluster-version --cluster-name X --kubernetes-version 1.34
  3. Wait for control plane — Monitor status (takes 10–30 minutes)
  4. Update node group — Update the launch template to the new AMI
  5. Enable node group auto-scaling — New nodes from updated AMI, old nodes gradually replaced
  6. Monitor node replacement — Existing nodes are replaced one at a time
PodDisruptionBudget (PDB) Blockers:
A workload with minAvailable: 1 on a 1-replica deployment blocks draining. The drain waits forever because no pod can be evicted. Solution: Temporarily lower the PDB or increase replicas before the upgrade.

Terraform: IaC Version Updates

AKS Terraform

resource "azurerm_kubernetes_cluster" "main" {
  name                = "aks-prod"
  kubernetes_version  = "1.35"  # Update this to trigger control plane upgrade

  default_node_pool {
    name             = "default"
    kubernetes_version = "1.35"  # Also update node pools
  }
}

# After applying, monitor with:
# kubectl get nodes -o wide

EKS Terraform

resource "aws_eks_cluster" "main" {
  name             = "eks-prod"
  version          = "1.35"  # Update control plane version

  depends_on = [aws_iam_role_policy_attachment.eks_cluster_policy]
}

resource "aws_launch_template" "nodes" {
  name_prefix = "eks-nodes-"

  block_device_mappings {
    device_name = "/dev/xvda"
    ebs {
      volume_size = 100
      volume_type = "gp3"
    }
  }
}

resource "aws_eks_node_group" "workers" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "workers"
  node_role_arn   = aws_iam_role.node_role.arn
  subnet_ids      = var.subnet_ids
  version         = "1.35"  # Node group version

  launch_template {
    id      = aws_launch_template.nodes.id
    version = aws_launch_template.nodes.latest_version_number
  }

  scaling_config {
    min_size     = 3
    max_size     = 10
    desired_size = 5
  }

  tags = {
    Name = "eks-worker-nodes"
  }
}

# After Terraform apply:
# aws eks describe-nodegroup --cluster-name eks-prod --nodegroup-name workers | jq .nodegroup.version

Common Failure Modes & Fixes

Failure Root Cause Fix
Drain times out Workload has PDB minAvailable but can't reschedule Increase replicas or suspend PDB temporarily
Evicted pods left behind Failed pods not cleaned up after drain Script auto-cleans with `kubectl delete pod --field-selector=status.phase=Failed`
Quota exhausted Cluster too full; new nodes can't be created Request higher quota or reduce workload
APM blocks EKS upgrade APM workload incompatible with new K8s version Remove APM during upgrade or wait for APM update
Kafka migration fails Zookeeper-to-KRaft migration job enabled on upgrade Disable job or increase job resources

Monitoring an Upgrade

# Watch node status
watch kubectl get nodes -o wide

# Check for stuck pods
kubectl get pods -A --field-selector=status.phase=Pending

# Verify control plane version
kubectl version --short

# Check for pod disruption budgets
kubectl get pdb -A

# Monitor events
kubectl get events -A --sort-by=.metadata.creationTimestamp
Idempotency: Both AKS and EKS upgrades are safe to retry. If the upgrade is interrupted, re-running it will skip completed phases and resume from where it stopped.
