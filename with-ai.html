What we did with AI

This portfolio was drafted with an AI assistant in the editor and reviewed before it was published. The assistant wrote the first version of the pages, the sample scripts, and the tests. The decisions stayed human: what was allowed to leave a work repository, which repo was private, and which plan was safe to run.

What got built

  • This site. A sidebar of concept pages for AWS, Azure, and CI/CD, plus later pages for interviews and security scans.
  • Profile README. A public summary of the skills, kept in the profile repository so the GitHub home page stays in the person's own words.
  • harbor-events-sample. An original multi-tenant event API: nested stacks, SigV4 and JWT, routing, and a two-region pipeline. The names and account ids in it are fictional.
  • multiarch-image-ci. A cloud-agnostic pipeline that builds amd64 and arm64 images and publishes one manifest.
  • aks-eks-upgrade-sample. A private planner for AKS and EKS. It walks one minor at a time, stops a node move when a PodDisruptionBudget allows no eviction, and calls Azure or AWS only when --execute is passed. The write-ups cover the upgrade, the budgets, and the infrastructure phases.
  • Cloud_CostSaving. Original scripts for idle-cloud cost: image expiry, unattached disks, nightly start and stop, and cluster scale-down. A normal run prints the plan.
  • Interview pages. Eight topics, 100 answered questions each, split into beginner, intermediate, and advanced: AKS, EKS, Terraform, Docker, Kubernetes, DevOps, Git, and CloudOps.
  • Security scans. Twistlock, Black Duck, FOSS, 2ms, Checkmarx, and Sonar, and why a pass on one does not clear the others.

What stayed out

  • Work repositories were read to understand the problem, then left where they were. The published scripts are new, not a copy of an internal tool.
  • Customer names, real account ids, certificates, and internal host names are not in these repos.
  • Anything that deletes or upgrades a live cluster is behind an explicit flag. The default command only prints a plan.

How that was more efficient

  • The first draft was the slow part, and it moved. A page, a script, and its tests arrived together. Review time went to correctness, not to a blank file.
  • One shape was reused. The upgrade scripts share the same hop rules. The interview pages share one layout. The cost scripts share the same dry-run habit. The second page did not start from zero.
  • Checks ran before a cloud call. Unit tests use fake clients. A version sequence or a closed budget fails in a second, with no subscription and no cluster.
  • Explanations stayed next to the code. Chat answers were written into the repo as point lists, so the next session did not depend on remembering the thread.
  • Scope stayed narrow. A request for a write-up became a page. A request for a live call became a flag. The assistant did not get a standing order to change production.
  • The human still approved the publish. Efficiency here is a shorter path from idea to a reviewed commit. It is not an unattended deploy.
