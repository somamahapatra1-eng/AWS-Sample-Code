What we did with AI

An assistant in the editor reads the work repositories, drafts the first version of an explanation or a change, and stops before anything mutates a live cluster. A person still decides what is published and what is applied.

On the integration work

The integration repository is a set of CloudFormation stacks, each with its own template and build spec.

  • Central API. API Gateway, attachment handling, and the build that packages them.
  • Lambda stack set. The publisher function, its layers, and the template that deploys them.
  • Teams integration. A template kept per release, so a fix is compared with the previous release instead of rewritten.
  • Surrounding stacks. Cross-account access, a Cognito foundation template, value-metric and notification stacks, and a small generative-AI resource template.

The assistant starts by naming the owning template. A question about the API does not turn into a search of the Lambda stack, and a release fix stays inside that release folder. Design notes were drafted from those templates and then accepted by a person. The work repository was not copied out.

On the infrastructure work

The infrastructure repository provisions the clusters with numbered OpenTofu modules. One config file holds the environment values. A deploy tool copies the provider file into each module, generates that module's backend, and runs init, plan, and apply as its own stack.

  • Azure foundation, then the cluster. Managed identity and private DNS zones come first. The cluster module only looks the zone up. Kubeconfig, storage class, DNS records, image trust, and the kubelet identity follow. A deprecated volume module is left out of the plan.
  • AWS foundation, then the cluster. Identity and security groups come first, then the cluster module, a security-group patch, interface endpoints, the load balancer, DNS, the image registry, and the endpoint service. Folders marked deprecated are skipped.
  • Gotchas the assistant checks before a plan. A node-pool label dropped in a config conversion does not fail apply, and pods then fail to schedule. Only pools that fit the regional quota are enabled. On a release upgrade, the existing config is merged into the new template before deploy.
  • Upgrades. The path is one minor version at a time. A runbook lists the pre-checks and the known failures. A live upgrade waits for approval.

That is the efficiency. The numbered folders already answer "what runs before the cluster." The assistant computes the hop list and the pre-checks from that layout. It does not get a standing order to apply.

What got built

  • This site. A sidebar of concept pages for AWS, Azure, and CI/CD, plus later pages for interviews and security scans.
  • Profile README. A public summary of the skills, kept in the profile repository so the GitHub home page stays in the person's own words.
  • harbor-events-sample. An original multi-tenant event API: nested stacks, SigV4 and JWT, routing, and a two-region pipeline. The names and account ids in it are fictional.
  • multiarch-image-ci. A cloud-agnostic pipeline that builds amd64 and arm64 images and publishes one manifest.
  • aks-eks-upgrade-sample. A private planner for AKS and EKS. It walks one minor at a time, stops a node move when a PodDisruptionBudget allows no eviction, and calls Azure or AWS only when --execute is passed. The write-ups cover the upgrade, the budgets, and the infrastructure phases.
  • Cloud_CostSaving. Original scripts for idle-cloud cost: image expiry, unattached disks, nightly start and stop, and cluster scale-down. A normal run prints the plan.
  • Interview pages. Eight topics, 100 answered questions each, split into beginner, intermediate, and advanced: AKS, EKS, Terraform, Docker, Kubernetes, DevOps, Git, and CloudOps.
  • Security scans. Twistlock, Black Duck, FOSS, 2ms, Checkmarx, and Sonar, and why a pass on one does not clear the others.

What stayed out

  • Work repositories were read to understand the problem, then left where they were. The published scripts are new, not a copy of an internal tool.
  • Customer names, real account ids, certificates, and internal host names are not in these repos.
  • Anything that deletes or upgrades a live cluster is behind an explicit flag. The default command only prints a plan.

How that was more efficient

  • The first hour was orientation, and it got shorter. Stack folders and numbered modules name the owner of a change before anyone edits. Review starts at the right template.
  • Known failures are checked before a cloud call. Label drift, quota, a closed disruption budget, and a version jump of more than one minor are caught in the plan. A bad plan fails without a subscription.
  • The first draft was the slow part, and it moved. A page, a script, and its tests arrived together. Review time went to correctness, not to a blank file.
  • One shape was reused. The upgrade scripts share the same hop rules. The interview pages share one layout. The cost scripts share the same dry-run habit. The second page did not start from zero.
  • Checks ran before a cloud call. Unit tests use fake clients. A version sequence or a closed budget fails in a second, with no subscription and no cluster.
  • Explanations stayed next to the code. Chat answers were written into the repo as point lists, so the next session did not depend on remembering the thread.
  • Scope stayed narrow. A request for a write-up became a page. A request for a live call became a flag. The assistant did not get a standing order to change production.
  • The human still approved the publish. Efficiency here is a shorter path from idea to a reviewed commit. It is not an unattended deploy.
